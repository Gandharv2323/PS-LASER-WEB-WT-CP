Part 2 — Introduction

Slide 3 — Introduction

On the slide

  • A laser-cutting job shop prices work from material, thickness, cut length, pierces, bends and finishing
  • PS Laser Web Platform automates this as a set of cooperating services over one shared schema
  • Contract-first design: one written contract fixes schema, JWT, price formula and API shapes
  • Heterogeneous stack by design: each service demonstrates one syllabus technology on real business data

Explain (technical notes for the speaker)

  • Technical framing: the platform is a request/response system. Clients send estimate, enquiry, tracking and login requests; staff users send updates; the system persists state in MySQL and emits events.
  • Why seven services: the course units cover PHP, Laravel, React, Servlet/JSP, Spring Boot, Advanced React and Node.js. Instead of seven toy demos, each technology implements a real feature of one business domain.
  • The risk of such a design is inconsistency. It is controlled by services/CONTRACT.md and by one reference test case that every implementation must reproduce.

Part 3 — Problem Statement, Aim and Objectives

Slide 5 — Problem statement

On the slide

  • P1 No automated computation of an indicative price from part parameters
  • P2 Enquiry intake is unstructured: requirements and drawing files arrive over telephone and chat
  • P3 Job progress is not exposed as queryable state
  • P4 Prices and job status are not maintained through a controlled, role-based interface
  • P5 Several heterogeneous technology stacks must stay consistent on one data model

Explain (technical notes for the speaker)

  • P1: price depends on area, weight, cut length, pierces, bends and coating. A manual calculation is slow and not reproducible.
  • P2: the shop's published channels are telephone and WhatsApp (four phone numbers and one WhatsApp number on the contact page). Files and requirements are not stored as structured records.
  • P3: no data model for job stages existed; the platform introduces work_orders and work_order_events with seven stages.
  • P5 is the course-level problem: PHP, Java, TypeScript and Node implementations must return identical money values.
  • Avoid claiming industry-wide statistics. State that the problem statement is specific to this shop.

Slide 9 — Comparison of architectural approaches and gap

On the slide

  • Monolith vs microservices vs multi-stack shared-schema (this project)
  • Shared database trades coupling for simplicity; mitigated by a contract and one reference test
  • Gap addressed: a single business domain implemented consistently across PHP, Java, TypeScript and Node.js

Explain (technical notes for the speaker)

  • Microservice literature (for example Newman, Building Microservices, and Richardson, Microservices Patterns) normally recommends a database per service.   • The cost of sharing is duplicated business rules in four estimators. The platform controls it with one formula specification, one rounding rule and one reference case that returns INR 2,933.83 on Spring, Next.js, PHP and the Servlet application [V, 14 Oct and 16 Oct 2026].
  • State the gap carefully: it is an engineering-integration gap for a course project, not a research gap in cost estimation.

Slide 16 — Architectural decisions

On the slide

  • Contract-first: services/CONTRACT.md before code
  • Shared schema with direct SQL for three applications
  • Backend-for-Frontend route handlers in Next.js
  • Graceful degradation: offline TypeScript estimate, demo data in the portal
  • Stateless authentication with HS256 JWT (8 h)
  • Event-driven side effects through domain events
  • One rounding rule: round each line half-up to 2 decimals, then add

Explain (technical notes for the speaker)

  • Each decision answers a risk: contract-first reduces integration drift; BFF keeps the Spring URL and JWT out of the browser bundle; domain events decouple logging and push from business logic; the rounding rule removes one-paisa differences between languages.
  • Events are published inside the transaction and delivered after commit, so a rolled-back status change never produces a push.

12.1 Technical viva questions with answers

Table 17. Question bank
#QuestionAnswer (technical)
1Why seven services instead of one application?Each CS3111 unit needs its own technology. One business domain implemented seven ways shows each technology on real data; a contract keeps them consistent.
2How do you guarantee the same estimate in four languages?One written formula, one rounding rule (round each line half-up to 2 dp, then add) and one reference case (INR 2,933.83) tested on Spring, Next.js, PHP and the Servlet application.
3Why BigDecimal in Java?Binary floating point cannot represent decimal money exactly; BigDecimal with HALF_UP gives deterministic two-decimal results.
4What is a BFF and why use it?Backend-for-Frontend: Next.js route handlers sit between the browser and the Core API. They validate input, keep the Spring URL and token out of the client bundle, and provide the offline fallback.
5Why is the JWT in an httpOnly cookie?JavaScript in the page cannot read it, which limits token theft through XSS. SameSite=Lax limits cross-site sending.
6How do Spring and Node.js share authentication?Both use HS256 with the same secret. Spring issues the token (claims sub, email, role, 8 h); Node verifies signature, expiry and role.
7Difference between SSR, SSG, ISR and CSR in your project?/track is SSR (per request); most pages are SSG; /quote is ISR with revalidate 3600; the calculator and live board are CSR islands.
8Why Zustand and Redux both?Redux Toolkit is Unit II (React Portal). Zustand is Unit V: small client state, selector subscriptions, persist middleware, no provider boilerplate.
9What does React.memo do and when is it useless?It skips re-render when props are shallow-equal. It does not help when props change every render (new function or object identity), which is why useCallback and a memoised input are used with it.
10useMemo vs useCallback?useMemo caches a computed value; useCallback caches a function reference. Both depend on dependency arrays.
11What is useTransition used for here?Filtering up to 10,000 parts: the input stays responsive and the stale list is dimmed while the filter renders at lower priority.
12How is real-time update implemented?Spring publishes WorkOrderStatusChanged after commit; ActivityEventListener sends a STOMP message to /topic/work-orders; the dashboard subscribes over WebSocket; polling every 15 s is the fallback.
13Why publish events after commit?If the transaction rolls back, no push or log should describe a change that did not happen.
14How are uploads secured?Type allow-list, 10 MB limit, content check (renamed executables are rejected), random private file names, download only for authenticated staff, rate limit.
15Why does tracking return 404 for a wrong phone?The response must not reveal whether an order number exists; both values must match.
16What is CORS and how is it configured?Browser rule on cross-origin calls. Each API allows an explicit origin list (3001, 5173, 8000, 8001, 8080 in development).
17Why share a database across services?Course units must stand alone and share one data model. The cost is duplicated rules; mitigated by the contract and the reference test.
18What does ddl-auto = validate mean?Hibernate checks entities against the existing tables at start-up and never creates or alters them, protecting the shared schema.
19Why work_orders and not jobs?Laravel owns a jobs queue table; a different name avoids the clash.
20How does the offline fallback work?The route handler has a 3 s timeout; on failure it runs the TypeScript copy of the formula and marks source = offline, shown by a badge.
21What is a discriminated union and where is it used?A union with a literal "kind" or "status" field that lets TypeScript narrow types, for example RequestState and TrackResult.
22How do you prevent stale responses in useEstimate?AbortController cancels the previous request and a request-id guard ignores out-of-order responses.
